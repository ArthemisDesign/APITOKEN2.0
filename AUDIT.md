# Архитектурный аудит claude-api

Снимок после серии работ по устойчивости (2026-07-12). Ниже — что построено, что уже
исправлено, и что **не предусмотрено / можно сделать лучше** (открытые пункты с приоритетами).
Источник: собственный разбор + независимый аудит-агент по всему коду.

## Что построено (эта сессия)

| Коммит | Суть |
|---|---|
| cache-first ядро | `pool::route`: сессии→персоны, пин по кэш-префиксу, спилл, capacity-weighted placement под конвертом конкуррентности |
| per-persona UA | `persona_ua`: флот перестал быть одним отпечатком (пул UA / разброс patch-версии) |
| HTTP/2 keepalive | событийная liveness транспорта вместо idle-таймаута |
| resilience | классификация вины 429/401/5xx, circuit breaker, 429+Retry-After при исчерпании |
| событийный поллер | probe только созревших, сон до due-времени (`select!` + `Notify`), не фикс-тик |
| durability | write-through персист cooling/калибровки — переживают рестарт |
| RAII-гарды | устранены утечки in-flight и резерва баланса при отмене запроса |

## Исправлено по итогам аудита

- **[CRIT] Утечка in-flight + резерва баланса при отмене запроса.** future хендлера дропается на
  `await` → `mark_used(+1)`/`reserve(hold)` не откатывались (ёмкость персоны копилась до рестарта +
  деньги клиента терялись). → **Фикс:** `InflightGuard`/`HoldGuard` (RAII), commit e7f5075.
- **[HIGH] Poison-запрос размыкал глобальный breaker в одиночку** (DoS всем). → **Фикс:** один запрос
  вносит в breaker максимум 1 backend-фейл.
- **[HIGH] 401/403 = 10с cooling** (долбёж мёртвого токена). → **Фикс:** карантин 900с.
- **[HIGH] 5xx студил подписку** за вину апстрима. → **Фикс:** `mark_done` без cooling + breaker.
- **[HIGH] Рестарт стирал cooling** (бан на дни забывался). → **Фикс:** write-through персист.
- **[CRIT] Trust-loopback за реверс-прокси** = аноним-админ. → **Фикс:** `trust_loopback` только при
  bind на loopback; экспонированный bind без ключей отклоняет всё (64702f4).
- **[HIGH] reload не видел смену token/proxy** того же email. → **Фикс:** `replace_subs` всегда (64702f4).
- **[HIGH] Резерв терялся при краше процесса.** → **Фикс:** леджер `reserved_nano` + `reconcile_reservations`
  на старте (64702f4).
- **[HIGH] Нет graceful shutdown.** → **Фикс:** `with_graceful_shutdown(SIGTERM/SIGINT)` — дренаж
  in-flight + финальный флаш (64702f4).
- **[MED] Нет наблюдаемости.** → **Фикс:** `/metrics` (Prometheus): cache-hit rate, in-flight, 429/
  auth/5xx, breaker, cooling. In-flight-gauge ловит регресс утечки слота.
- **Refresh OAuth-токенов** — сознательно НЕ делаем: токены годовые, revoked рефрешем не спасти,
  900с-карантина для редкой ревокации достаточно.

## Открытые находки — что НЕ предусмотрели (по приоритету)

> CRIT/HIGH из первой волны (trust-loopback, reload-по-содержимому, леджер резервов, graceful
> shutdown) и MED-наблюдаемость — **закрыты** (см. раздел выше). Ниже — оставшееся.

### MED

5. **Калибровка ломается при использовании аккаунта владельцем.** Подписка — живой Max-аккаунт;
   расход владельца двигает `util` без нашего `spent` → `cap=Δutil/Δspend` занижается. *Направление:*
   калибровать только когда наш расход доминирует Δutil, иначе лишь ре-заякориваться.
6. **`plan` (pro/max5/max20) детектится, но не используется.** Прайор ёмкости — единый под Max20 →
   Pro-подписка переоценивается → 429-штормы до калибровки. *Направление:* сидить per-sub прайор из `plan`.
7. **Multi-instance split-brain.** Всё состояние пула in-memory; два инстанса бьют один аккаунт,
   `pool_state` last-writer-wins, affinity не общая. Деньги безопасны (SQLite reserve/settle атомарны).
   *Направление:* документировать «один serving-инстанс» / общий стор горячего состояния / advisory-lock.
8. **Identical-prefix batch схлопывается на одну персону.** Много запросов с общим префиксом →
   один session_key → одна персона (спилл лишь сверх `MAX_INFLIGHT`). *Направление:* шардировать
   высокочастотные сессии (подмешивать hash%N при занятости дома) / детект batch → load-based.

### LOW

10. **util 1% → 100%.** `v>1.0 ? v/100 : v`: значение `1` (1%) трактуется как 100% → подписка зря
    исключается. *Направление:* фиксировать единицу unified-заголовка, не эвристику.
11. **bindings не персистятся** → холодный prompt-cache после каждого деплоя (осознанный тредофф).
12. **Обрыв стрима после 200** → недосчёт биллинга/калибровки, клиент получает SSE без `message_stop`
    и без явного error-события. *Направление:* инжектить SSE-`error` + метрика обрыва.
13. **Порог breaker зависит от QPS** (абсолют 12/10с), не от доли фейлов. *Направление:* rate-based.
14. **Единый `Mutex` пула** — потолок масштабируемости горячего пути (для скромного QPS ок).
15. **web_search-стоимость не в потолке резерва** → возможен микро-овердрафт. Незначительно.
16. **`reload_loop` (30с) и safety-flush (120с) всё ещё периодичны** — кросс-процессный онбординг
    подписок не событийный. *Направление:* сигнал от CLI/authbot (файл/сокет) вместо опроса БД.

### Не доведено по дизайну (осознанно)

- **Per-persona конверт неполон:** есть потолок конкуррентности (`MAX_INFLIGHT`), но нет
  rate-джиттера и циркадной формы нагрузки (естественность живого юзера) — верхняя планка стелса.
- **Actor-per-persona** не реализован буквально: его цель (событийность, отказ от скана) достигнута
  событийным поллером на одном `Mutex`-состоянии. Отдельные акторы — опциональная будущая структура,
  оправданная в основном при переходе к shared-state / multi-node.

## Рекомендованный следующий заход

Приоритетные CRIT/HIGH + наблюдаемость закрыты. Из оставшегося вперёд стоит: **plan → per-sub
прайор** (MED #6 — иначе Pro-подписки штормят 429 до калибровки, дёшево) и **калибровка при чужом
использовании** (MED #5 — точность ёмкости на реальных живых аккаунтах). Затем LOW-гигиена (util 1%,
обрыв стрима). Multi-node (#7) — только при переходе на 2-й сервер. **Главное сейчас — прогон на
живой подписке:** движок ещё ни разу не проверен вживую, `/metrics` (route_pin/place, inflight) даст
первую объективную картину cache-hit и утечек.
