# Распределение запросов по подпискам: принятый план эффективности трат квот

> Решение по итогам анализа и двух раундов ревью (2026-08-20). Из десяти диагнозов и семи
> предложений исходного анализа оставлены только подтверждённые кодом правки, которые
> заметно улучшают распределение квот по флоту, **не ломая кэш-экономику**: пин Claude и
> sticky-аффинити Kimi/GLM/Codex/Gemini остаются неприкосновенными. Отклонённое — в §5,
> с причинами; не предлагать заново без данных из §6.
>
> Провенанс: исходный анализ — `67361653`, расширение на Gemini/Kimi — `982ef22f`,
> ревью №1 — по коду `9d2f6201`, ревью №2 — по коду `e41bd99a`; их фактические поправки
> (формула R7, семантика `quota_rank` Codex, GLM) свёрнуты в текст ниже.
>
> Плоскости: **Claude** (окна 5h + 7d, `crates/pool`), **GPT/Codex** (5h «primary» +
> недельное «secondary», `crates/forward/src/codex`), **Gemini** (per-модельные бакеты
> официального квота-каталога Google, `crates/forward/src/gemini`), **Kimi** (5h-rolling +
> недельное окно, точные `used/limit/resetTime`, `crates/forward/src/kimi`) и **GLM**
> (селектор зеркален Kimi при собственной таксономии `Ineligible`, `crates/forward/src/glm`).

## 1. Текущая логика

### 1.1 Claude pool (`crates/pool/src/lib.rs`)

**Состояние на подписку:** измеренная ёмкость окон `cap5h_usd/cap7d_usd` (калибровка
ΔUSD/Δutil из трафика, EMA α=0.3, кламп к план-масштабированному прайору ×[0.25; 4]),
«живая» утилизация `live_util` (последний заголовок + наш расход после него, прошедший reset
обнуляет окно), cooling, in-flight, durable auth-вердикт.

**Запас (Reserve):** мягкий потолок `1 − base` с детерминированным джиттером по email
(5h: 10% ± 2%; 7d: 3% ± 2%). Под пиком фильтр ослабляется до `FULL` (до 100%) — клиенту лучше
запрос у стены, чем синтетический 429.

**Cache-first роутинг (`route`)** — единица планирования сессия, а не запрос:

1. **Пин** — свежая привязка (idle < 1h, TTL кэша) к дому, который жив, не за потолком
   и не в глубоком cooling (≥ 60с) → тот же дом, даже если весь остальной флот пуст.
2. **Спилл одного запроса** — дом «наш», но временно занят (бёрст-cooling < 60с или
   in-flight ≥ 6): запрос уходит на `select_best_non_cooling`, привязка сохраняется.
3. **Пере-привязка / новое размещение** — дом мёртв/за потолком/в глубоком бане:
   capacity-weighted `place_best` — из элигибельных (под резервом, под конвертом in-flight)
   выбирается максимум `placement_free = min(cap5·(1−util5), cap7·(1−util7))`, тай-брейки:
   меньше in-flight, дальше LRU.

**Ретраи/обычный выбор (`pick`/`select_best`):** min по иерархии
`cooling → конверт in-flight → over_cap → util7d → util5h → warning → in-flight → LRU`.
Ключевой приоритет: **7d-утилизация сравнивается раньше 5h** — недельный бюджет дефицитнее
(прайор: 7d ≈ $1500 против 33 окон 5h ≈ $1650/неделю).

**Cache-root (общий системный префикс):** `peek_affinity_home_with_warm` — прогреваем минимум 2
дома, тёплый предпочитается, пока его `placement_free ≥ ratio ×` глобальный максимум;
`route_affinity` продолжениям разрешает жёсткий потолок 100% (вместо мягкого резерва) —
тёплый кэш важнее запаса.

### 1.2 GPT/Codex fleet (`crates/forward/src/codex/mod.rs`)

**Состояние:** провайдер отдаёт `usedPercent` по окнам (primary 5h, secondary weekly) +
авторитетные флаги `allowed`/`limit_reached`. USD-калибровка ёмкости есть
(`CodexWindowCapacityReport`), но **в выборе не участвует** — только в операторских отчётах.

**Резерв (WindowReserve):** то же 5h 10% / 7d 3% ± джиттер по home id; окно за
джиттерованным порогом → дом исключается до ближайшего reset (`reserve_blocked`). Жёсткое
исключение — только провайдерский вердикт (`reached`, `allowed: false`); `usedPercent=100` с
`allowed: true` ещё обслуживает. Под пиком двойной escape-hatch: ослабление резерва до FULL,
затем игнор собственного мягкого cooling.

**Выбор (`select_home`):** кандидаты сортируются по
`fast_rank → snapshot_stale → in-flight → seed (только для новых) → quota_rank → курсор ротации`:

- **quota_rank** — грубый стиринг: `(max_used_percent − 50) / 10`, т.е. ниже 50% окна
  квота вообще не влияет на порядок, выше — бакеты по 10 п.п. Сделано намеренно, чтобы
  курсор ротации равномерно размазывал равных кандидатов и не было «стада на самом пустом».
  Важно: `max_used_percent()` — это максимум по primary **и** secondary, а не недельный
  процент; большую часть недели ранг рисует 5h-окно.
- **Аффинити:** разрешённый разговор (preferred) — жёсткий первый выбор внутри лучшего
  Fast-класса (без проверки quota/in-flight в момент выбора — дом уже прошёл admission с
  резервом). Новый общий cache-root — 2 тёплых дома, затем предпочтение тёплого
  (`CACHE_ROOT_MIN_WARM_HOMES`).

### 1.3 Gemini fleet (`crates/forward/src/gemini/pool.rs`)

**Состояние:** официальный квота-каталог Google — per-модельные бакеты с `remaining_fraction`
и временем reset (окна разные по моделям, фиксируются в `GeminiWindowCapacityReport`); плюс
два независимых cooling-контура: мягкий «environment» (наша инференция из 401/транспорта) и
жёсткий quota-cooling (Google ответил 429 на бесплатный вызов → профиль реально вне квоты).

**Резерв:** per-профиль × per-модель джиттерованный порог
(`quota_reserve_fraction` деф 5% ± 1%). Профиль с остатком ниже резерва отфильтровывается,
**но только пока есть хоть один профиль с запасом** — иначе резерв снимается со всех
(service floor, не изобретаем outage раньше официального нуля).

**Выбор (`select_routed_inner`):** сортировка
`preferred (жёсткая аффинити) → snapshot_stale → in-flight → quota_rank → курсор`:

- **quota_rank** — та же схема, что у Codex: ниже 50% окна квота не влияет, выше — бакеты
  по 10 п.п. (зафиксированный урок: exact fraction-first sorting заставлял чуть более пустой
  профиль поглощать весь бёрст, пока квота не догоняла).
- **Аффинити:** разрешённый разговор — жёсткий первый выбор при любой квоте выше жёстких
  гейтов. Новый cache-root — 2 тёплых профиля (`CACHE_ROOT_MIN_WARM_PROFILES`), дальше
  тёплый предпочитается без квота-проверки близости.
- **Escape-hatch:** `select_routed_ignoring_env_cooling` ослабляет только мягкий
  environment-cooling; жёсткий quota-cooling и официальный ноль не ослабляются никогда.

### 1.4 Kimi fleet (`crates/forward/src/kimi/selection.rs`)

**Состояние:** провайдер отдаёт точный `used/limit/resetTime` по окнам (5h-rolling +
недельное); durable-состояние (`health.quota_windows` в `kimi/gateway.rs`) хранит **все**
окна целиком — `duration_secs`, нативные `used/limit`, `used_fraction_units`, `resets_at`,
`observed_at`. Но в селектор попадает только свёртка — **самое тесное окно**
(`used_fraction_units`, fixed-point 10⁻⁸) и его возраст. Жёсткие вердикты: `QuotaWall`
(провайдерский отказ до reset), `CapabilityNotInPlan`, `ModelCooling`, `AuthQuarantined`,
`TransportWedged`.

**Выбор (`select`):** ранг `(freshness → in-flight → steering)` + курсор ротации по связанным:

- **freshness:** свежее наблюдение (≤ 300с) > не-наблюдался (нейтрально, не «полон») > протухшее.
- **steering:** точная доля самого тесного окна, но **только при ≥ 50%**; ниже — все равны.
- **Аффинити:** `sticky` выигрывает безоговорочно, пока профиль элигибелен. Упёртый в стену
  sticky проваливается на общий выбор, не фейля запрос.
- **Софт-резерва нет вообще:** профиль роутится до провайдерского QuotaWall, escape-hatch
  ослабляет только environmental-причины (урок Gemini августа 2026: волна 401 девять раз
  обнуляла здоровый пул).
- **Локального лимита конкуррентности нет:** `inflight` — сигнал размещения, не потолок.

### 1.5 GLM fleet (`crates/forward/src/glm/selection.rs`)

Ядро ранга дословно зеркалит Kimi (freshness → in-flight → стиринг с полом 50% → курсор;
sticky-first; та же свёртка окон максимумом в `glm/gateway.rs`), но таксономия `Ineligible`
своя и осознанно другая: `QuotaWall / AccountDead / AccountSuspect / ModelIneligible /
TransportWedged`, без environmental-развилки в селекторе (статический ключ не «оживает» от
ослабления). Любая правка селектора Kimi обязана прийти сюда зеркальной правкой — но НЕ
общей абстракцией (общий модуль потребовал бы общей таксономии, а её различие — свойство
плоскостей, не дублирование).

### 1.6 Где во всём этом время до reset

Reset сегодня участвует в решениях только как **граница**, не как градиент:

1. прошедший reset обнуляет окно (Claude `live_util`; у остальных — свежий снапшот);
2. срок исключения дома — до reset переполненного окна (`reserve_blocked` Codex,
   `quota_cool_until` Kimi/GLM, quota-cooling Gemini);
3. Retry-After клиенту при полностью лимитированном флоте;
4. у Claude — прогноз ёмкости флота в операторском снапшоте (в роутинг не попадает).

Ни один селектор не взвешивает *время до* reset при живом выборе: дом с 90% пятичасового
окна за 10 минут до сброса ранжируется так же плохо, как дом с 90% недели. Принятые правки
R1/R7 добавляют системе именно эту отсутствующую ось.

## 2. Что уже сделано правильно (не трогать)

- **Приоритет 7d над 5h в Claude** — недельное окно связывает (7d < сумма 5h-окон), и его
  бережение важнее: правильный дефолт.
- **Reserve с джиттером** + escape-hatch до FULL под пиком — баланс «не долбить стену» и
  «не отказывать клиенту».
- **Живая утилизация** (заголовок + наш расход) компенсирует лаг провайдерских заголовков.
- **Кэш-аффинити с дешёвым спиллом** — дом сохраняется при краткой занятости, rebind только
  при реальной потере (мертв/за потолком/длинный бан).
- **Codex: нормализация по проценту своего окна** — тарифно-агностично; стиринг только у
  стены (≥ 50%), бакетами, чтобы не ломать fan-out курсором.
- **Codex: провайдерские вердикты как единственный жёсткий стоп** — не жжём живые аккаунты
  из-за грязного `usedPercent=100`.
- **Gemini: раздельные контуры cooling** и service floor (резерв снимается со всего флота,
  когда запаса нет ни у кого).
- **Kimi/GLM: sticky проваливается на общий выбор при QuotaWall**, а не фейлит запрос;
  never-observed профиль нейтрален, а не «полон».

## 3. Подтверждённые кодом проблемы (под каждую есть принятая правка)

Нумерация исходного анализа сохранена для трассируемости; диагнозы, не прошедшие проверку
или не имеющие измеренной величины потерь, перечислены в §5.

### П2. Claude placement: `min(free5h, free7d)` наливает новые сессии на «5h-свежие, 7d-выжженные» дома
Максимум `placement_free` выигрывает у подписки с только что сброшенным 5h даже при высоком
util7d. Новые сессии концентрируются на ней и дожигают её же 7d — самоподдерживающийся
«недельный слив» одних и тех же домов. Доказано механически: тест `conserves_weekly_budget`
покрывает только `pick`/`select_best`, где 7d уже решает; `place_best`/`route` — нет.

### П5. Резервы статичны по времени окна — квота недотрачивается в хвосте
Цель запаса — не упереться в стену раньше reset; за часы до reset запас уже не нужен, а
квота пропадает (Codex 3% недельного, 10% пятичасового; Gemini 5%; Claude 3%/10%). Время до
reset нигде не входит в решение (§1.6), хотя данные для него уже есть во всех плоскостях.

### П10. Kimi/GLM: стиринг по свёртке окон в одно число
`used_fraction_units` — свёртка 5h и weekly до селектора: 90% 5h-окна при пустой неделе и
90% недели при пустом 5h неразличимы, хотя первое сбросится через полчаса, а второе — через
дни. Плюс отсутствие какой-либо градации перед провайдерским QuotaWall: флот доезжает до
стены «внезапно». Важно: durable-данные обоих окон **уже лежат** в `health.quota_windows`
(включая `resets_at`) — теряются они в одной строке свёртки `max()` при сборке `Candidate`.

## 4. Принятые правки

Критерий отбора: заметное выравнивание трат квоты по флоту при нулевом или почти нулевом
влиянии на кэш (пин и sticky не трогаются ни одной из правок).

### R2. Claude: учитывать 7d в placement новых сессий
`placement_free = min(free5h, free7d)` заменить нормированным скорингом
`score = min(free5/cap5, free7/cap7) − λ·util7`, λ ≈ 0.5–1.0 (нормированный вариант
обязателен: абсолютный член `λ·cap7` ~$750–1500 забил бы `free5` ~$50). Новые сессии
перестают налипать на «5h-свежие/7d-выжженные» дома; 5h-дефицит всё равно решает через min,
а 7d-порядок наследуется из `select_best`, где 7d уже главный.
**Кэш не затронут вообще** — правка касается только размещения новых сессий.
**Тест** — рядом с `conserves_weekly_budget`, но на `place_best`/`route` новых сессий,
не на `pick`.

### R7. Kimi + GLM: разложить стиринг по окнам и добавить мягкий запас у стены
Прокидывать в `Candidate` оба окна (данные уже в durable-снапшоте, см. П10):

- стиринг считается по weekly **отдельным ключом ранга** (длинный ресурс решает размещение),
  не свёрткой в одно число;
- 5h учитывается с дисконтом по близости reset: `eff5 = used5 · min(1, time_to_reset5 / 3600)`
  — окно, которое сбросится через 10 минут, почти не пугает. (В исходном анализе формула
  была инвертирована — `min(1, 3600/t)` давал полный вес окну у самого reset; исправлено
  ревью №1, арифметика перепроверена ревью №2.)
- мягкий запас только у самой стены: при `weekly ≥ 95%` профиль доступен только для
  sticky-продолжений (кэш дороже), новые размещения идут на других; escape-hatch при пустом
  флоте сохраняется. С существующим жёстким контуром (`quota_cool_until` из окон на ≥100%)
  не конфликтует — встраивается уровнем ниже.

**Кэш не затронут:** sticky по-прежнему выигрывает безоговорочно, вплоть до стены.
**GLM — зеркальной правкой** (один коммит или пара соседних) с зеркальными тестами; общий
селектор не извлекать (§1.5). **Тесты** — рядом с `quota_steering_only_applies_near_the_wall`
и escape-hatch тестами обеих плоскостей.

### R1 v1. Codex: pace-aware резерв (time-decay джиттерованного порога)
Эффективный резерв `base·f(t)`, где `f` линейно убывает от 1 к ~0.15 за последние ~6 часов
недельного окна и последний час 5h-окна. Реализация — внутри
`WindowReserve::window_cap`/`reserve_blocked`: окна уже несут `resets_at` и
`window_duration_mins`, новая сантехника не нужна. Обязательные предохранители:

- **масштабируется джиттерованный порог**, не общий clock — синхронный weekly-reset пачкой
  купленных домов не должен дать «стадо в стену»;
- **pace guard:** не ослаблять резерв, если `текущий_темп × time_to_reset > remaining`
  (с запасом) — time-decay сам по себе не гарантирует, что reset наступит раньше стены.

**Границы эффекта (знать заранее):** под пиком резерв и так ослабляется до FULL, поэтому R1
выигрывает только в хвостах окон вне пика; верхняя оценка — размер резерва × доля домов,
доезжающих до конца окна заблокированными резервом без пикового ослабления. Эту долю даёт
шаг 0 из §6.
**Расширение на Claude/Gemini — только второй волной**, после того как Codex-decay не поднял
429 и метрики подтвердили величину потерь: на Claude pace guard опирается на калиброванные
`cap5h/cap7d` (EMA, кламп ×[0.25; 4]) — оценку с погрешностью до крат, нужен консервативный
запас; Codex же получает проценты и reset от провайдера точно.
**Кэш не затронут** — резерв влияет только на admission новых размещений, преференции
продолжений (`route_affinity` до 100%, sticky) не меняются.

## 5. Отклонено и что НЕ менять

Осознанные свойства (не баги — любая будущая правка обязана их сохранить):

- **Курсор ротации и анти-herding на Codex/Gemini/Kimi/GLM**; провайдерские вердикты как
  единственный жёсткий стоп; **Kimi/GLM `inflight` — сигнал, не потолок**; **Gemini service
  floor**; **джиттер резервов** (R1 масштабирует джиттерованный порог, не заменяет);
  **escape-hatch до FULL под пиком**; **калибровка ёмкости Claude** и запрет использовать
  эфемерные quota-снапшоты как durable-историю; **спилл одного запроса с сохранением
  привязки**.

Отклонённые предложения исходного анализа (не предлагать заново без данных из §6):

- **R3 (rebind продолжений у 7d-стены) и R5b (квота-взвешивание sticky/preferred)** —
  ломают кэш при каждом срабатывании: цена определённа и немедленна (полный input без
  cache-read на префиксе, ~10× цена хода), выигрыш в распределении не измерен. На Kimi/GLM
  «sticky выигрывает, пока элигибелен» — сознательная экономика, зафиксированная в
  комментариях кода. Возврат к теме — только если метрики §6 покажут, что пин/sticky
  реально дожигают недели, и cache-hit это переживёт.
- **R4 (непрерывный quota-стиринг, пол 25–30%, бакеты 5 п.п.)** — ставка против
  задокументированного регресса Gemini (exact-fraction herding); посылка о накапливающемся
  расхождении утилизаций не измерена. Плюс ранг Codex — `max(primary, secondary)`, а не
  недельный процент: R4 в исходной формулировке калибровал бы не ту величину. Если
  измерения покажут проблему — сначала решить, что ранжируем, потом канар с полом 40% и
  бакетом 10 п.п. на одном провайдере.
- **R5a (квота-порог для тёплого дома при размещении новых cache-root)** — отложено во
  вторую волну: риск низкий (цена — один холодный прогрев), но величина эффекта не измерена.
- **R6 (cost-aware давление по preflight-оценке цены хода)** — preflight-токены на
  tools/reasoning врут; cost-aware давление на грязной оценке хуже percent-стиринга.
  Не начинать, пока R1/R2/R7 не сдвинули вариацию утилизаций.

## 6. Порядок внедрения и наблюдаемость

Порядок (каждая правка — отдельный маленький коммит с тестом рядом с существующими):

0. **Измерение** (без кода селектора; определяет вторую волну и размер эффекта R1):
   гистограммы `util7d` (Claude) / `max_used_percent` (Codex) / tightest fraction (Kimi/GLM)
   / `remaining_fraction` (Gemini) по флоту в T−24h и T−2h до reset; доли pin/spill/rebind и
   cache-hit (`cached_input_tokens / input_tokens`); синхронность weekly-reset по флоту;
   доля домов «5h пустой при 7d на резерве» (это и есть теряемая ёмкость).
1. **R2 (Claude placement)** — новые сессии, кэш цел, П2 доказан в коде.
2. **R7 (Kimi + GLM парой)** — оба окна в `Candidate`, weekly отдельным ключом, дисконт 5h
   по времени, мягкий запас у стены.
3. **R1 v1 (Codex)** — time-decay джиттерованного порога + pace guard.
4. **Вторая волна — только по метрикам:** R1 на Claude/Gemini (после того как Codex-decay
   не поднял 429), R5a (тёплые cache-root).

Контроль эффекта:

- распределение `util7d` / tightest fraction по флоту на конец недели — вариация должна
  снизиться после R2/R7;
- доля домов на 7d-резерве до конца недели — цель R1 ≈ 0 до последних часов;
- `route_rebind / (pin+place)` и cache-hit `pin/(pin+place)` — **не должны измениться**:
  принятые правки кэш не трогают, дрейф этих метрик = регрессия, а не эффект;
- частота провайдерских 429 — цель R1: не вырасти;
- GLM — в тех же дашбордах, что Kimi.
