## 1. Резюме

Сейчас есть ровно один стенд — производственный. Локальные тесты, smoke-прогоны с mock-upstream и
exact-SHA валидация кандидата дают сильный, но не полный фильтр: систему целиком (engine + commerce +
worker + router + Caddy + БД) в связке, под нагрузкой и с реальными сценариями деградации проверять
негде. При частых деплоях часть регрессий переживает все гейты и проявляется на клиентах.

Предлагается ввести **второй стенд (stage) — контур-близнец прода**, размещённый **на том же VPS,
что и прод**, но в полностью отдельном пространстве имён: свой ОС-пользователь, свои корни
каталогов (`/opt/apitoken-staging`, `/srv/claude-api-staging`, …), свой диапазон портов, свой
PostgreSQL-контейнер, свой набор systemd-юнитов и жёсткие cgroup-лимиты по CPU/памяти. Та же
структура каталогов, те же шаблоны юнитов, тот же watchdog-конвейер и blue-green, но свои секреты,
своя БД, свой (по умолчанию mock-) апстрим и полностью закрытый сетевой доступ (никакие клиенты
не могут до него достучаться). Разработка идёт **stage → prod**: ветка `stage` является триггером
стенда, в `master` (триггер прода) код попадает только после зелёной валидации на stage и
утверждения. **Хотфиксы** имеют отдельный быстрый путь сразу в `master` с обязательным последующим
сведением `stage` с `master`.

Ключевое отличие от обычного "заведи второй сервер": стенд получает **гейт обнаружения
деградации** — постоянную синтетическую нагрузку с профилем прод-трафика и A/B-сравнение синего и
зелёного слотов на одном и том же трафике, плюс пороговые правила по метрикам. Регрессия ловится
до прода не эпизодической проверкой "вручную посмотрели", а автоматическим red-статусом, который
блокирует promotion.

## 2. Текущая модель доставки (как есть)

Факты, на которых стоит план (детали — в указанных документах):

1. **Trunk-based.** `master` — единственный триггер производства. В него нельзя коммитить напрямую;
   единственный путь — `git push` + `deploy/agent-merge.sh`, который берёт merge-lock, перебазирует
   ветку, гоняет path-aware гейт, ждёт зелёный `deploy/watchdog`.
2. **Хост-watchdog на проде.** Поллит `master` каждые 5 секунд, валидирует точный SHA
   (path-aware: TypeScript/DB лайны, Rust лайны, операционные регрессионные сьюты), перед
   выкаткой снимает валидированные бэкапы БД, применяет forward-only миграции, затем
   blue-green: engine-слоты Anthropic 8787/8788, OpenAI 8793/8797, Gemini 8795/8799, API 3000/3001,
   router 8800/8801; финальная проверка — синтетические пробы (`/ready`, contract-пробы OpenAI/Gemini).
3. **Кандидат-валидация до мержа.** `deploy/agent-merge.sh` просит прод-хост протестировать точный
   SHA фиче-ветки в изолированном окружении (свои порты, своя БД, свой Cargo target), до попадания
   в `master`. Это де-факто "тест на проде в песочнице", а не отдельный стенд.
4. **Тесты.** `cargo test` (в т.ч. обязательные money-тесты), pnpm build/typecheck/test,
   интеграционные тесты против disposable PostgreSQL, smoke-сценарии с mock upstream
   (`tests/rotation_fanout_smoke.sh`, `tests/universal_chat_smoke.sh`, `tests/mock_upstream.py`
   с реалистичными unified-ratelimit заголовками и thinking-блоками).
5. **Фронтенд-превью.** Для `apps/web` есть независимый канал: ветки `preview/*` дают Vercel
   pre-production деплой с человеческим ревью до мержа. Для backend/engine/инфраструктуры
   эквивалента нет.
6. **Мониторинг.** Полный стек (Prometheus/Grafana/Loki/Alertmanager + экспортеры) только на проде.
   Внешний uptime-детектор — GitHub Actions. Метрики, дашборды и правила — из репозитория
   (`observability/`).
7. **Провайдеры.** Флот живых подписок (Claude Max/Pro, Codex, Gemini). Live-гейты новых моделей и
   canary на транзитных loopback-портах выполняются **на прод-хосте**.

## 3. Недостатки текущей модели

Отсортированы по важности; каждый пункт — конкретный класс риска, который стенд закрывает.

- **Один контур без "среды сборки системы".** Engine, commerce, worker, router, Caddy, БД впервые
  встречаются вместе только в проде. Кандидат-валидация на проде изолирует один SHA, но не
  проверяет систему под нагрузкой и не даёт наблюдать её после выкатки. Ошибки взаимодействия
  компонентов — самая частая причина деградации, которую юнит-тесты не видят.
- **Частые деплои × серийный конвейер = почти нет окна наблюдения.** Каждый merge в `master` — это
  полный прод-цикл, а следующий merge встаёт следом. Между "выкатили" и "выкатили следующее"
  нет обязательного периода соака/наблюдения. Регрессия с отложенным проявлением (медленный рост
  ошибок, деградация под нагрузкой) смешивается со следующим деплоем, и причину инцидента трудно
  атрибутировать.
- **Деградацию не с чем сравнить.** Финальный пост-деплой гейт (`docs/ops/DEPLOYMENT.md`) проверяет
  "живо и отвечает контракту", но не сравнивает метрики до/после выкатки: латентности, долю
  4xx/5xx, поведение ротации, использование слотов. Медленная деградация проходит зелёной.
- **Смоуки завязаны на mock upstream.** Реальное поведение подписок (паттерны 429, пределы окон,
  «util5h»-динамика, SSE-особенности) проверяется только на живом проде после выкатки, либо
  дорогими калибровками по `docs/ops/*_CALIBRATION.md`.
- **Forward-only миграции на проде.** Схему нельзя откатить бинарным rollback — только новым
  корректирующим коммитом (а это стресс под прод-нагрузкой). На стенде защита остаётся той же,
  но цена неудачной миграции — ноль для клиентов, и отработку можно довести до автоматической.
- **Инфраструктурные изменения едут сразу в прод.** `deploy/`, `systemd/`, `observability/`
  обновляются прод-watchdog'ом автоматически. Изменения самого конвейера (трюки с sudoers,
  установкой юнитов, рендером Caddy) проходят только регрессионными сьютами, но не пробным
  прогоном деплоя на небоевом хосте.
- **Предпросмотра бэкенда для человека нет.** Фронтенд имеет Vercel Preview c человеческим ревью,
  бэкенд/движок/инфраструктура — нет. При разборе инцидентов негде воспроизвести точный
  прод-релиз отдельно от клиентского трафика (среда для воспроизведения = прод-хост).
- **Live-гейты провайдеров выполняются на прод-хосте.** Транзитные canary-порты, fenced-корни
  и live-запуски (GPT Image и аналоги) живут на боевом сервере; изоляция — на уровне процесса
  и каталога, а не контура.
- **Прод-хост перегружен обязанностями.** Гейт + кандидат-валидация + канарейки + прод-трафик на
  одной машине: тестовая активность может влиять на боевую (и наоборот). Совмещённый стенд
  добавляет на этот хост ещё один контур, поэтому весь раздел 5.2 построен вокруг одного
  требования: **стенд обязан деградировать сам, но никогда — прод** (ресурсные лимиты,
  приоритеты, раздельные пространства имён).

Что уже хорошо и что план сознательно **не ломает**: изоляция через worktree, сериализованный
мерж с lock, exact-SHA неизменяемые релизы, blue-green, forward-only дисциплина миграций,
принцип «всё из репозитория, секреты только на хосте». Всё это переиспользуется на стенде
1:1, а не изобретается заново.

## 4. Цели и не-цели

**Цели:**

- G1. Существует стенд, поведенчески неотличимый от прода (та же сборка из того же SHA, те же
  юниты, те же пути, тот же конвейер), на котором разработка валидируется до прода.
- G2. Поток доставки: task-ветка → `stage` → авто-деплой на стенд → автоматический и человеческий
  контроль → promotion в `master` → прод.
- G3. Есть быстрый путь хотфикса в `master` в обход стенда, с обязательным последующим
  схождением `stage` с `master`.
- G4. Клиенты взаимодействуют только с продом. Стенд не имеет публичных маршрутов; доступа к нему
  у клиентов нет по конструкции (нет публичного DNS, firewall, tunnel-only).
- G5. Регрессия/деградация, прошедшая юнит-тесты, ловится на стенде автоматически
  (базлайны метрик, A/B слотов, пороги) и блокирует promotion.
- G6. Отказ стенда никогда не блокирует хотфикс-путь в прод (прод остаётся автономным).
- G7. Прямая доставка в `master` запрещена без исключений: ни ручных пушей, ни «мелких» байпасов.
  Единственный путь — через скрипты мержа; для аварий — явный хотфикс-поток с обязательным
  последующим схождением `stage` с `master`.
- G8. Флот подписок провайдеров существует в одном экземпляре, и управлять им (пополнение,
  ротация, лизинги, health) может только прод-контур. Стенд и хотфикс-кандидаты используют
  емкость флота только через контролируемый прод-интерфейс (shadow-read, см. 5.3.1), никогда —
  через прямое владение токенами или запись в прод-БД движка.

**Не-цели (сознательно исключено):**

- Не вводится полноценное канареечное развертывание прода (X% трафика на новый релиз). Сначала —
  стенд с A/B слотов; canary-сложность вернётся позже, если понадобится.
- Не строится DR-резерв: стенд живёт на том же хосте, что и прод, и в принципе не переживает
  отказ хоста. Авария хоста роняет оба контура — это принятый компромисс совместного размещения.
- Не переносится биллинг/деньги: стенд работает на своей БД с синтетическими деньгами.
- Не роем chaos engineering как отдельную дисциплину — только целевые сценарии деградации
  в нагрузочном генераторе.
- Не меняются межконтекстные контракты (Control API, sales feed): стенд их потребляет в том же
  виде, что и прод.

## 5. Целевая архитектура: два контура-близнеца

### 5.1 Базовый принцип

Один репозиторий, два контура-близнеца на одном хосте. **Всё, что можно, берётся из репозитория
идентично**: Cargo-workspace и pnpm-workspace собираются из одного SHA; `deploy/`, `systemd/`,
`observability/` — общие. Контур-specific — только секреты (env-файлы), имя ветки-триггера,
диапазоны портов и сетевые правила. Уже сегодня почти вся конфигурация host-specific вынесена
в `/etc/apitoken/*` и `/srv/claude-api/data/*` — этот же принцип переносится на стенд (со своими
путями), что само по себе закрывает основной источник дрифта между контурами. Совместное
размещение вдобавок гарантирует нулевой дрифт инструментов (одни и те же Node/Rust/Postgres/Caddy
живут на одной машине) — это второй по важности аргумент выбранного варианта.

Различия стенда от прода (полный перечень — раздел 7.4) должны быть явными и минимальными.

### 5.2 Размещение на общем хосте и изоляция контуров

| Параметр | Прод (как есть) | Стенд (цель) |

| ОС-пользователь | `deploy`, root-бриджи, `apitoken-ci` | отдельный `deploy-stage` (+ `stage-ci` для тестовых процессов); стенд-процессы не работают от прод-пользователей и наоборот |
| Каталоги | `/opt/apitoken/releases`, `/srv/claude-api/releases`, `/var/lib/apitoken/...` | свои корни: `/opt/apitoken-staging`, `/srv/claude-api-staging`, `/var/lib/apitoken-staging` — ни одного общего пути с продом |
| Порты | 5433, 8790–8805, 3000/3001, 6379/6380 | свой диапазон (по умолчанию «+10000»: движок 18790/18787/18788, OpenAI 18792/18793/18797, Gemini 18794/18795/18799, KIMI 18803–18805, router 18800–18802, API 13000/13001, commerce 18791; PostgreSQL **5434**, Redis стенда 16379/16380; mock upstream — отдельный порт). | systemd-юниты | `apitoken-*`, `claude-api-*` | те же шаблоны с суффиксом `-stage` (`apitoken-api-stage@.service`, `claude-api-anthropic-stage@.service`, …) — прод-watchdog не видит stage-инстансы, его топологические проверки не меняются |
| PostgreSQL | контейнер `apitoken-postgres`, `127.0.0.1:5433`, прод-БД | отдельный контейнер `apitoken-postgres-stage`, `127.0.0.1:5434`, свои volume и роли (см. 5.4) |
| Ресурсы | весь хост | **жёсткий бюджет стенда** через systemd: `MemoryMax`/`CPUQuota`/`TaskMax` на каждом stage-юните + `Nice`/`IOSchedulingClass` ниже прод-класса для билдов; цель — стенд умирает от нехватки ресурсов сам, но не отбирает их у прода |
| Публичные маршруты | все продуктовые vhost'ы | **нет ни одного.** Caddy стенда слушает только loopback; клиенты недостижимы по конструкции |
| Доступ оператора/агентов | SSH `deploy` + приватные vhost'ы | SSH + проброс портов (`ssh -L`), интерфейсы стенда (Grafana, панель) через тот же туннель |
| Firewall | UFW deny-inbound, SSH/HTTP/HTTPS | без изменений: стенд не слушает внешние интерфейсы вовсе; новые входящие правила не заводятся |
| DNS | `*.apitoken.sale` | отсутствует (режим туннеля; публичное имя для стенда не заводится) |
| Секреты | `/etc/apitoken/*`, `/srv/claude-api/data/*` | собственные файлы в **стенд-корнях** (`/etc/apitoken-staging`, `/srv/claude-api-staging/data`), mode 0600, чтение только для стенд-пользователей; **ни один прод-секрет не копируется и не становится читаемым для стенда** |

#### Инварианты совместного размещения (не обсуждаются)

1. Ни один stage-процесс не запускается от прод-пользователей; ни один прод-процесс — от
   стенд-пользователей.
2. Никаких пересечений корней релизов, БД, Redis, дампов, секретов и lock-файлов между контурами.
   Пути стенда всегда и только с суффиксом `-staging`.
3. Ресурсные лимиты стенда настраиваются до запуска первого stage-юнита; превышение бюджета
   давит стенд (OOM/сброс его процессов), а не прод.
4. Stage-watchdog работает с приоритетом кандидат-валидаторов (прецедент на проде уже есть —
   low-priority host workers), со своими lock'ами и state-каталогами; он никогда не трогает
   прод-lock, прод-релизы и прод-статусы.
5. Стенд-миграции и стенд-операции никогда не касаются прод-контейнера PostgreSQL
   (`apitoken-postgres` остаётся неприкосновенным); стендовый контейнер можно пересоздавать
   свободно.
6. Бэкап-таймер прода не захватывает стенд-БД (имена дюмпов разные, каталоги разные); при
   желании — отдельный дюмп-таймер стенда, но без влияния на прод-цепочку.

#### Что даёт совместное размещение (в сравнении с отдельным VPS)

- Ноль затрат на второй сервер; нулевой дрифт инструментов и ОС-слоя;
- переиспользование уже оттестированного SHA: промоушен-коммит, который стенд уже собрал и
  провалидировал, прод-конвейер может взять из существующего root-owned кандидат-кэша (та же
  механика, что уже описана для candidate-validation) вместо повторной сборки;
- общий наблюдательный стек: Prometheus/Grafana прод-хоста дополнительно скрейпит стенд
  с меткой `env=staging`, отдельный стенд-дашборд, алерты стенда — низким severity или только в
  стенд-отчёт (раздел 8), чтобы не шуметь в прод-мониторинге.

#### Что берём на себя (осознанные компромиссы)

- Общий failure domain: хост, питание, диск, Docker — одна точка отказа для обоих контуров.
- Ресурсная конкуренция (CPU билдов, RAM, диск, iops) между контурами — управляется лимитами и
  приоритетами (инвариант 3/4), но не устраняется полностью.
- Ошибка оператора в одном контуре потенциально ближе к другому (правильные пути/порты —
  вопрос дисциплины и суффиксов). Таблица портов и путей из этого документа — обязательная
  часть provisioning'а фазы 1.

Стенд не имеет CORS-пересечений с боевым фронтом (`NEXT_PUBLIC_BACKEND_URL` прод-сайта указывает
на прод, и не меняется). «Клиенты не могут попасть на стенд» обеспечивается на уровне сети,
а не только конфигурации приложения.

### 5.3 Подписки провайдеров на стенде

Это самое чувствительное место (живые подписки стоят денег и банятся при неаккуратных тестах).
Исходное требование владельца: **флот подписок один, управляет им master, но стенд и
хотфикс-кандидаты должны мочь его использовать.** Прямая трактовка «стенд читает прод-флот»
небезопасна и отклонена — причины и рабочая альтернатива ниже.

#### 5.3.1 Почему прямое разделение флота невозможно, и что вместо этого

Флот подписок — это не статичный список токенов, а stateful-система:

- окна лимитов 5h/7d живут в головах провайдеров и в PG-авторити движка
  (`docs/engine/STAGE2_POSTGRES_AUTHORITY.md`);
- в `crates/pool` держится in-memory состояние ротации: лизинги, health-статусы, «rebind»-связи
  клиент↔подписка, счётчики 429;
- `CLAUDE_API_UPSTREAM` — глобальная настройка инстанса движка (`crates/server/src/config.rs`),
  per-account маршрутизации апстрима в коде нет: один инстанс либо ходит в реальный
  `api.anthropic.com`, либо целиком в mock.

Следствие: второй движок, ходящий теми же токенами в тех же провайдеров, неизбежно (а) пишет
два независимых представления о состоянии подписок (окна, health, лизинги) — движок потеряет
единый авторити; (б) сжигает реальные лимиты прод-флота тестовым трафиком; (в) своими
429-волнами и неаккуратными паттернами ухудшает health и рискует баном прод-подписок.

**Принятая модель: один флот — один владелец, остальные — клиенты по HTTP.**

- Управляют флотом только прод-инстансы (`claude-api`, authbot, прод-registry) — единственный
  писатель в авторити, единственный держатель in-memory пула. Это инвариант уровня G8.
- Стенд и хотфикс-кандидаты **не получают живых токенов и не пишут в прод-БД движка**.
  Доступ к емкости флота они получают двумя способами, оба опциональны и включаются
  отдельным решением оператора:

  1. **Shadow-read состояния флота (фаза 5+, рекомендуется).** Прод-движок уже отдаёт
     телеметрию подписок через Control API (operator telemetry, `docs/engine/CONTROL_API.md`).
     Стенд-наблюдатель скрейпит её read-only: окна, health, доля исчерпанных — чтобы
     degrade-гейт и генератор нагрузки стенда калибровали mock-поведение по реальному
     профилю флота (паттерны 429, динамика окон). Никакой записи, никаких токенов.
  2. **Бюджетный live-endpoint (фаза 7, строго опционально).** Если mock-реализма мало,
     стенд может ходить в **прод-флот как обычный API-клиент**: на проде заводится отдельный
     engine-аккаунт `stage-live` с собственным ключом `sk-pool-…` и жёстким nanoUSD-капом
     (переиспользуется дисциплина капов из `docs/ops/*_CALIBRATION.md`, стартовый бюджет —
     центы). Трафик стенда идёт через тот же публичный/внутренний endpoint прода, что и
     трафик любого клиента: ротацией, лимитами и health флота по-прежнему управляет только
     прод-движок. Это единственный безопасный смысл фразы «стенд использует флот»:
     как потребитель сервиса, не как совладелец. Хотфикс-кандидаты используют тот же
     endpoint в своих live-пробах, если оператор его включил.

- Чего в модели сознательно **нет**: расшаривания `subscriptions.db`/PG-авторити между
  контурами, копирования живых токенов в стенд-секреты, read-replica пула. Любое из этих
  трёх — нарушение G8 и блокер мержа.

- **Песочница (опционально, фаза 7)** — из прежнего плана остаётся как третий, независимый
  вариант: отдельный минимальный набор реальных подписок (низкие тарифы, выделенные
  аккаунты, НЕ из прод-флота), свой `authbot` на стенде. Дешевле и безопаснее, чем
  live-endpoint, но требует отдельных денег и обслуживания. Если live-endpoint включён,
  песочница скорее не нужна.

- Прод-флот никогда не используется стендом на запись, стенд-флот (песочница) никогда не
  используется продом — это инвариант уровня секретов и уровня правил.

#### 5.3.2 Дефолтный режим стенда

- **Дефолт — mock upstream.** Движок стенда стартует с `CLAUDE_API_UPSTREAM` =
  mock-сервер, поднятый на стенде из тех же механик, что `tests/mock_upstream.py`, расширенный
  сценариями: окна 5h/7d, 429-волны, «мёртвая подписка», замедление стримов, обрыв SSE. Подписки
  в БД стенда — синтетические, с фейковыми токенами. Никаких живых токенов.
- Сценарии mock-апстрима калибруются по shadow-read телеметрии прод-флота (5.3.1), когда она
  включена: это закрывает главный недостаток mock-режима — расхождение профиля с реальностью.

### 5.4 Данные стенда

- Свой PostgreSQL: отдельный контейнер `apitoken-postgres-stage` на `127.0.0.1:5434` того же
  хоста, свои volume и роли. Свои БД: `commerce`, `claude_engine`, `sales`, `openkeys`
  (CRM не нужен — не его контур). Прод-контейнер (`apitoken-postgres`, 5433) стенд не трогает
  никогда — ни соединениями, ни перезапусками.
- Redis стенда (позже, для fidelity affinity/history) — отдельные инстансы на своих портах
  (16379/16380); на первых фазах движок в mock-режиме работает без них (тесты со
  `CLAUDE_API_TEST_REDIS_URL` проходят в стенд-лайне со своим disposable Redis).
- Наполнение: **сгенерированный seed** (новый скрипт, см. фазу 3): аккаунты и ключи, балансы,
  заказы в sandbox-статусах, referral-строки, mock-подписки, тарифные и provider-строки, чтобы
  повторять форму прод-данных без реальных PII. Схема — всегда из тех же миграций, что и прод:
  расхождение схем само по себе является сигналом.
- Прод-дам из прод-бэкапа **не** используется. Позже (фаза 7) — опционально скрабленный
  анонимизированный дамп, если реализма seed'а окажется мало. Это отдельное решение
  с собственным скраб-конвейером (PII, токены, почты, суммы), не раньше закрытия стандартных фаз.

### 5.5 Commerce-безопасные заглушки

Стенд должен «проживать» все те же воркфлоу без внешних эффектов:

- Платежи — sandbox-ключи провайдеров (Platega/Cryptomus sandbox), либо локальная заглушка, если
  провайдер не даёт sandbox.
- Почта — sink (Mailhog/локальный SMTP), либо devbot-стиль запись в лог; ни одно реальное письмо
  и ни один webhook наружу не уходит.
- OAuth Google/GitHub — отдельные stage-приложения разработчика.
- Внешний uptime-workflow (`.github/workflows/production-uptime.yml`) на стенд не распространяется.

## 6. Git-модель: `master` + `stage` + hotfix

### 6.1 Ветки

- `master` — без изменений: интеграция и прод-триггер, только через `deploy/agent-merge.sh`.
- **`stage` (новая)** — интеграция и стенд-триггер. Защищена от прямых пущей так же, как master.
  Может опережать `master` на несколько утверждённых на стенде изменений, но не должна
  расходиться с ним навсегда.
- Task-ветки (`feat/*`, `fix/*`, `docs/*`) — от `origin/master`, обычный поток, без изменений.
- **`hotfix/*`** (новая семантика) — от последнего зелёного `master`; короткоживущая ветка
  аварийного исправления.

### 6.2 Поток разработки (stage → prod)

```text
origin/master ─┬─ feat/foo ─────...─────▶ (1) merge в stage ──▶ стенд: тесты, миграции, blue-green
               │                                        │       + degrade-гейт + человеческое утверждение
               │                                        └─────▶ (2) promotion: merge stage → master
               │                                                    └─▶ прод: обычный watchdog-цикл
               └─ feat/bar ─────...──┐
                                     └── (независимо) ...
```

1. **Merge в `stage`.** Тот же `deploy/agent-merge.sh` с явно заданными переменными окружения
   (скрипт уже параметризован — см. `deploy/agent-merge.sh:25-35`):
   `AGENT_MERGE_TARGET=stage`, `AGENT_MERGE_REQUIRED_CONTEXT=deploy/stage`,
   отдельный lock (`AGENT_MERGE_LOCK=.../stage-merge.lock`), отдельная validation-environment
   (`AGENT_MERGE_VALIDATION_ENVIRONMENT=staging-candidate-validation`). Удобно оформить как
   тонкую обёртку `deploy/agent-merge-stage.sh`, чтобы агент не набирал переменные руками.
2. Стенд-watchdog (раздел 7) тестирует точный SHA, мигрирует stage-БД, выкатывает blue-green
   и публикует `deploy/stage` (overall) и компонентные контексты.
3. После зелёного `deploy/stage` работает degrade-гейт и (для изменений, затрагивающих клиентский
   фронтенд) обычное Vercel-превью с ревью. **Утверждение promotion — операторское**: агент
   не продвигает stage без явной команды (аналог текущего правила про превью).
4. **Promotion.** Из ворктри ветки `stage` запускается тот же `deploy/agent-merge.sh` с
   `AGENT_MERGE_TARGET=master` и требуемым контекстом `deploy/watchdog`. В `master` попадает
   протестированное содержимое; прод проходит обычный цикл. (Если важна история
   «коммит-за-коммитом» вместо одного rebase-потока — promotion выполняется последовательными
   мержами отдельных task-веток; механика та же, решает оператор. По умолчанию —
   rebase-поток stage целиком.)
5. **Схождение.** После успешного promotion стенд-ветка приводится к `master`: `stage` =
   `master` (плюс недопромоученные кандидаты, если есть). Единственный разрешённый способ —
   скрипт `deploy/stage-sync.sh` под тем же merge-lock: он делает fast-forward/promote `stage`
   к новому `master` и пушит. Прямые `git push -f` ветки `stage` агенту запрещены (заносится в
   правила наравне с master).

### 6.3 Хотфикс (в обход стенда)

```text
origin/master ─▶ hotfix/x ──▶ merge сразу в master (deploy/agent-merge.sh, обычный гейт)
                                   │
                                   └─▶ сразу после зелёного deploy/watchdog:
                                       deploy/stage-sync.sh подтягивает hotfix в stage,
                                       стенд получает то же исправление обычным циклом
```

- Хотфикс — это merge в `master` без предварительной валидации на стенде, но **не без гейтов вообще**:
  локальный gate + кандидат-валидация + `deploy/watchdog` остаются обязательными. Обходится только
  стадийный цикл (стенд + утверждение).
- Ветка называется `hotfix/*`, commit-сообщение явно фиксирует причину обхода стенда и контекст
  аварии. Правило миграций не меняется: хотфикс с миграцией — два коммита, migration-first.
- Если хотфикс пришёл, пока `stage` содержит недопромоученные изменения, stage-sync нормально
  справляется: `stage` переуточняется на новый `master`, а недопромоученные кандидаты
  перемерживаются поверх (rebase автоматически переносит их на свежий master; конфликт
  разрешается обычным процессом `deploy/agent-merge-recover.sh`).
- Стенд, будучи впереди, никогда не блокирует хотфикс — прод-контур автономен (G6).

### 6.4 Что меняется в правилах для агентов (фаза 2)

- `BRANCHES.md`: добавить строку `stage` (владелец, триггер стенда, правила схождения) и раздел
  hotfix (критерии обхода стенда, документирование).
- `AGENTS.md`: поток «merge в stage → утверждение → promotion», запрет `git push -f` в `stage`,
  обязанность использовать `deploy/agent-merge-stage.sh` / `deploy/stage-sync.sh`.
- `CONTRIBUTING.md`: описание двухступенчатой доставки, `deploy/stage` как пред-триггера прод,
  критериев обхода стенда для hotfix.
- Индексы `docs/README.md` и карта в `AGENTS.md` — по факту добавления новых документов.

### 6.5 Запрет прямой доставки в `master` — техническое закрепление

Правило «в `master` только через `deploy/agent-merge.sh`» действует и сегодня, но обеспечено
дисциплиной и хуком, который работает не везде. В фазе 2 оно закрепляется технически:

1. **GitHub branch protection на `master`** (и на `stage`): запрет прямых пушей для всех, включая
   администраторов; required status checks — `deploy/watchdog` (для `master`) и `deploy/stage`
   (для `stage`); запрет force-push и удаления ветки. Единственный пушист — служебный
   merge-ключ, которым владеет только `deploy/agent-merge.sh` на хосте оператора.
2. **Promotion-прекондишн на стороне скрипта:** `deploy/agent-merge.sh` в `AGENT_MERGE_TARGET=master`
   дополнительно проверяет, что для того же дерева есть зелёный `deploy/stage`, если только
   ветка не `hotfix/*` (см. 8.3). Это делает обход стенда невозможным «по забывчивости».
3. **Без байпаса для «мелочей».** Исходный открытый вопрос №5 («только docs/ и тесты — сразу в
   master») закрыт отказом: цена прохождения мелочи через стенд минимальна (лайны path-aware,
   docs-only дифф не собирает Rust/TS), а прецедент исключения размывает сам инвариант.
   Единственный обход стенда — явный `hotfix/*` с документированной причиной (раздел 6.3).
4. **Хотфикс не отменяет гейтов.** Хотфикс обходит только стадийный цикл (стенд + человеческое
   утверждение); локальный gate, кандидат-валидация и зелёный `deploy/watchdog` обязательны.
   Прямого `git push origin master` не существует ни для кого, ни при каких обстоятельствах.

## 7. Конвейер доставки на стенде

### 7.1 Стенд-watchdog

На том же хосте работает **вторая линия того же** watchdog-комплекта (`deploy/install-watchdog.sh`),
сконфигурированная под контур стенда и отделённая от прод-линии пространством имён:

- поллится ветка `stage` (тот же read-only деплой-ключ репозитория);
- свой state-root (`/var/lib/apitoken-staging/watchdog`), свои lock-файлы, свои quarantine-маркеры;
  стенд-конвейер никогда не пишет в прод-статусы и прод-quarantine, и наоборот;
- работает с пониженным приоритетом (Nice/IOSchedulingClass уровня существующих
  low-priority candidate-валидаторов) и в пределах ресурсного бюджета стенда (инварианты 3/4
  раздела 5.2), чтобы гейт/билд стенда не давил прод-трафик;
- тот же path-aware отбор лайнов, те же изолированные disposable БД/Cargo-таргеты, но внутри
  стенд-пространства (свои порты PostgreSQL/Rust-кэшей, свои `.next/cache`-объекты);
- миграции — только на стенд-БД (5434); blue-green — на стенд-слотах (порты «+10000» из 5.2);
- статусы GitHub: новые контексты `deploy/stage` (overall) и компонентные `deploy/stage-*`
  (engine/backend/migration), deployment-записи в environment **`staging-environment`**.
  Публикуются через существующий root-owned reporting-бридж (он расширяется именами контекстов);
  отдельного root-кредишенса для стенда не заводится;
- прод-специфичные одноразовые гейты (gpt-image-*, live-калибровочные контроллеры, devbot
  прод-топики) у стенд-линии **не активны** (полный список выключений фиксируется в `deploy/README.md`
  при реализации фазы 2);
- бэкап-политика стенда минимальна (перед миграциями — дампы stage-БД в стенд-каталог; Borg
  off-host — только если оператор решит, что стенд этого заслуживает). Прод-цепочка
  (`claude-api-backup.timer`, ежечасные дюмпы) стенд-БД не захватывает.

Схема «две линии одного комплекта на одном хосте» уже имеет прецедент: low-priority
candidate-validators сосуществуют с серийным прод-watchdog'ом на текущем проде; стенд-линия
проектируется как постоянный третий участник с тем же классом приоритета и собственным
неймспейсом состояния.

Возможные переиспользуемые уже сейчас куски (проверено по коду): параметризация
`AGENT_MERGE_TARGET` / `AGENT_MERGE_REQUIRED_CONTEXT` / `AGENT_MERGE_LOCK` в `deploy/agent-merge.sh`,
машинерия `.github`-статусов (`deploy/watchdog-github.sh`), НЕ требует смены формата — только
новых имён контекстов.

### 7.2 Порядок деплоя на стенде

Зеркально проду, без исключений: тесты → дампы/бэкапы → миграции под локом → неактивный слот
(миграции движка транзакционные, `/ready`) → health-gate → cutover → пост-деплой пробы →
degrade-гейт (раздел 8) → статусы. Провал любой стадии — red `deploy/stage`,
quarantine-SHA. Роллбек на проде работает; на стенде — тот же `rollback.sh` + **автоматический**
откат при red degrade-гейта (на стенде это безопасно, и это отдельный ценный сценарий, который
прод сегодня не репетирует).

### 7.3 Вёрстка секретов стенда

Все env-файлы стенда заводит оператор один раз (фаза 1), в репозиторий не попадают.
Набор — зеркало продового, но с заменёнными значениями: свои пароли БД, свои контрольные ключи,
движок в mock-режиме, почта-заглушка, платежи-sandbox. `CONTROL_KEY` стенда — отдельный.

### 7.4 Полный список сознательных отличий стенда от прода

Этот список — часть документа-контракта, всё остальное поведение совпадает:

1. Триггер — ветка `stage`, статусы — `deploy/stage*`, environment — `staging-environment`.
2. Нет публичных маршрутов, только loopback/туннель.
3. Движок по умолчанию на mock upstream; прод-подписки стенду не принадлежат и не
   адресуются им напрямую; доступ к емкости флота — только по модели 5.3.1 (shadow-read
   телеметрия и/или бюджетный live-endpoint как API-клиент).
4. БД — своя, seed-данные; прод-дампы не используются (опционально скраб в фазе 7).
5. Платежи/почта/OAuth — sandbox/заглушки.
6. Прод-специфичные live-гейты и внешний uptime-детектор не активны.
7. Бэкапы — локальные, упрощённая ротация.
8. Роллбек при red degrade-гейта — автоматический (на проде — по решению оператора).
9. Ресурсы — жёстко ограниченный бюджет (MemoryMax/CPUQuota, заниженные приоритеты) на общем
   хосте; стенд держит форму, а не пропускную способность прода.
10. Совместное размещение: общий хост, ОС и Docker с продом — изоляция исключительно
    пространством имён (пользователи, каталоги, порты «+10000», юниты `*-stage`, свой
    PostgreSQL 5434) и ресурсными лимитами, по инвариантам раздела 5.2.

## 8. Обнаружение деградации (ядро ценности стенда)

### 8.1 Постоянная синтетическая нагрузка с профилем прод-трафика

- Новый генератор нагрузки (скрипт в репо, напр. `deploy/stage-load/`): работает на стенде
  постоянно (низкая интенсивность) и умеет burst-режим на время последеплойного окна.
- Сценарии покрывают профиль прод-трафика, видимый в метриках: messages stream/non-stream
  (в т.ч. thinking), роутер `/v1/messages` и универсальный чат, responses API, `/balance`,
  ошибочные пути (невалидный ключ, исчерпанный баланс, отмена стрима на середине),
  «спящие» доли трафика по провайдерам.
- Интенсивность калибруется так, чтобы НЕ выжигать лимиты mock-пула, а лишь создавать
  измеримый поток метрик. Burst не обязан равняться пику прода — важен стабильный, сравнимый
  профиль. Генератор работает под стенд-пользователем и в пределах ресурсного бюджета стенда
  (раздел 5.2): давление на общий хост ограничено по построению, чтобы нагрузочные прогоны
  не конкурировали с прод-трафиком.

### 8.2 A/B между синим и зелёным слотами

Blue-green механика уже умеет держать два слота двигателя/API. На стенде после выкатки кандидата
старый слот **не выключаем в окне сравнения**: оба слота живут, генератор шлёт одинаковый поток
трафика в каждый (или слот-квоту 50/50 через туннели), метрики снимаются по слотам раздельно.
Итог — прямое сравнение «старый релиз vs кандидат» на идентичном трафике, чего прод делать не может.

Продолжительность окна сравнения настраивается (дефолт-предложение: 15 минут burst; для изменений
движка/маршрутизации — до часа под постоянной нагрузкой). После окна — обычный cutover; старый
слот уходит по штатному drain.

### 8.3 Золотые метрики и пороги (degradation gate)

Стенд-watchdog после деплоя вызывает новый скрипт `deploy/stage-degrade-gate.sh`, который сравнивает
кандидат с базлайном (тот же слот до выкатки или параллельный старый слот — раздел 8.2) по списку
«золотых» метрик. Пороги — данные в репозитории (напр. `deploy/stage-degrade-thresholds.tsv`),
обновляются с обычной дисциплиной коммитов:

- латентность запросов p50/p95, время до первого байта стрима;
- доля клиентских 4xx и серверных 5xx, `customer_http_error`-события;
- ротация: `429`-ретраи, «rebind»-события, усреднённое число попыток на запрос;
- служебное здоровье: заполнение billing-очереди, латентность PG-команд, inflight, утечки
  лизингов/резервов;
- ошибки роутера (fallback-rate, admission failures) и Caddy upstream health.

Правила гейта: регрессия пороговой величины на любой метрике = red `deploy/stage` + авто-роллбек
стенда (см. 7.2) + запрет promotion; движение в пределах допуска — желтая зона (запись в отчёт,
не блокирует); деградация, причинно объяснимая сценарием самого деплоя (например, изменение
формата ошибки) — оператор может разблокировать с письменной причиной (аналог `--fix-red`).

Промоушен-прекондишн на клиенте: `agent-merge.sh` в target=master дополнительно проверяет, что
`deploy/stage` зелёный на том же содержимом; для веток `hotfix/*` — не проверяет (обход стенда
явный, см. 6.5). Проверка реализуется на существующей машинерии статусов
(`deploy/watchdog-github.sh`): достаточно запросить контекст `deploy/stage` для merge-SHA,
новых кредишенсов не требуется.

### 8.4 Регулярные проверки, которые стенд берёт на себя

- Миграции: commerce-миграции прогоняются на stage-БД *до* попадания в прод — отлавливается
  ошибка миграции как таковой, а не её влияние на прод.
- E2E-протоколы поверх живого стенда: ChatGPT-протокол, стриминговые сценарии, паритет
  `staging` — аналоги `tests/universal_chat_smoke.sh`, но по реально развернутой системе.
- Репетиции роллбека: автоматический роллбек стенда — регулярный (еженедельный) тренировочный
  сценарий, который прод не репетирует вручную.
- Деградационные инъекции (фаза 5): генератор умеет сценарии падений (убить слот, затормозить
  PG, обрубить поток SSE), чтобы правила гейта проверялись регулярно и не «протухали».

## 9. Фазы внедрения

Каждая фаза — отдельные коммиты и зелёные статусы; документы обновляются в тех же коммитах.
Оценки — грубые (человеко-дни оператора + доля агентской работы).

- **Фаза 0. Решения — ВЫПОЛНЕНА (v4, 2026-08-16).** Все вопросы закрыты владельцем
  (раздел 10.1): бюджет ≤ 8 GB / ≤ 2 ядер / ≤ 50 GB, доступ только SSH-туннель, протекающий
  стенд, песочница в фазе 7, флот — shadow-read до решения после фазы 5. Ресурсный бюджет и
  портовая таблица подтверждены живым снятием состояния прод-хоста. Закупать нечего.
- **Фаза 1. Provisioning стенда на общем хосте (1–2 д).** Всё делается на `84.32.48.2`
  без остановки прод-контура: пользователь `deploy-stage`, стенд-корни
  (`/opt/apitoken-staging`, `/srv/claude-api-staging`, `/var/lib/apitoken-staging`,
  `/etc/apitoken-staging`), секреты сгенерированы заново (стенд-значения, не копии продовых),
  контейнер `apitoken-postgres-stage` на `127.0.0.1:5434` со своим volume, cgroup-лимиты
  (`MemoryMax`/`CPUQuota`/`TaskMax`) в stage-шаблонах юнитов, таблица портов «+10000»
  зарезервирована. UFW не меняется (внешние интерфейсы стенд не слушает). `docs/ops/INFRASTRUCTURE.md`
  получает секцию «Staging contour (co-located with production)»: топология, порты,
  пространства имён, грань изоляции — всё из раздела 5.2.
- **Фаза 2. Ветка `stage` и конвейер стенда (2–4 д).** Защита ветки; скрипты
  `deploy/agent-merge-stage.sh`, `deploy/stage-sync.sh` (+ регрессионные сьюты рядом с
  существующими `.test.sh`); стенд-линия watchdog на том же хосте (поллинг `stage`, контексты
  `deploy/stage*`, environment `staging-environment`, расширение существующего root-owned
  reporting-бриджа новыми именами контекстов, список выключений 7.4); обновление
  `BRANCHES.md`, `AGENTS.md`, `CONTRIBUTING.md`, `deploy/README.md`.
  Коммиты миграции-first, как обычно.
- **Фаза 3. Данные стенда (1–2 д).** Seed-генератор (форма БД максимум повторяет прод-форму,
  содержание синтетическое), прогон в стенд-лайне после миграций; роль и БД стенда; запрет
  прод-дампов зафиксирован в доках. Добавить `deploy/stage-seed` + его тест.
- **Фаза 4. Компоненты стенда (2–3 д).** Движок в mock-режиме (улучшенный mock upstream с
  деградационными сценариями), commerce API/worker, sales, openkeys, роутер, Caddy стенда на
  loopback, подключение стенда к существующему мониторинг-стеку (скрейп с меткой
  `env=staging`, отдельный стенд-дашборд; алерты стенда не смешиваются с прод-алертами
  по severity). Каждый контекст — своим лайном/юнитами `*-stage`, как на проде.
- **Фаза 5. Гейт деградации (2–4 д).** Генератор нагрузки, A/B слотов, пороги
  `deploy/stage-degrade-thresholds.tsv`, `deploy/stage-degrade-gate.sh`, авто-роллбек,
  прекондишн promotion. Приёмка фазы: искусственная регрессия (инъекция) ловит гейт,
  promotion блокируется — демо-прогон фиксируется в аудите.
- **Фаза 6. Хотфикс-поток и переход на новую модель (1–2 д).** Валидация сценария хотфикса
  на тренировочном примере, drill всего цикла (stage-merge → degrade-gate → promotion → hotfix →
  stage-sync), обновление рунбуков (`docs/ops/DEPLOYMENT.md` и новый runbook стенда). С этого
  момента поток stage→prod обязателен для всего, кроме hotfix.
- **Фаза 7. Опциональное усиление (по решению оператора).** Песочница реальных подписок
  (+перенос канареечных live-гейтов провайдеров с прод-контура на стенд-контур), скрабленный
  анонимизированный дамп для данных, контроль конфигурационного дрифта контуров (проверка,
  что обе линии применяют одинаковые `deploy/`, `systemd/`, `observability/`; дрифт инструментов
  исключён самим совместным размещением).

## 10. Риски и решения фазы 0

Риски:

- **Общий failure domain.** Хост, питание, диск, Docker и UFW общие: аппаратная авария или
  ошибка на уровне хоста роняют оба контура сразу (в варианте с отдельным VPS прод был бы
  изолирован). Принято владельцем осознанно; стенд по определению не DR-резерв.
- **Blast radius стенда на прод.** Билды стенда, burst нагрузки и стенд-миграции могут
  конкурировать за CPU/RAM/iops/диск. Митигируется инвариантами 5.2 (cgroup-лимиты, заниженные
  приоритеты, раздельные каталоги/порты/БД) и мониторингом бюджета стенда как прод-предупреждения.
- **Ошибка оператора между контурами.** Перепутанные порт/путь/юнит на общем хосте бьют
  дальше, чем на разных машинах. Митигируется жёсткими суффиксами (`-staging`, «+10000»),
  отказом стенд-скриптов принимать прод-пути и таблицей из 5.2 как части provisioning'а.
- **Двойной контур = двойное обслуживание.** Митигируется: всё из репозитория, тот же
  watchdog-комплект (вторая линия), все секреты контур-специфичны; дрифт контролируется
  в фазе 7. Всё же стенд потребует бюджета внимания при обновлениях конвейера.
- **Стоимость.** Серверного бюджета больше нет; остаются (в фазе 7) отдельные подписки
  песочницы — фиксируются отдельной строкой.
- **Стенд даёт ложное спокойствие.** Реализм mock-апстрима ограничен; живые паттерны провайдеров
  стенд увидит только с песочницей. Поэтому правила: живой провайдерский GA — по-прежнему через
  существующую дисциплину (`docs/engine/PROVIDER_ONBOARDING.md`, калибровки), стенд её дополняет,
  а не заменяет.
- **`stage`-ветка и force-операции.** Сведение stage к master по сути force. Ограничено одним
  скриптом под локом; аварийные русла описаны в 6.3.
- **Задержка доставки.** Двухступенчатый цикл удлиняет путь в прод. Для аварий — хотфикс-поток
  (раздел 6.3); байпаса для «мелочей» нет (6.5): дисциплина важнее сэкономленных минут, а
  docs-only/тестовые диффы проходят стенд дёшево за счёт path-aware лайнов.
- **Стенд как клиент прод-флота (риск v3).** Если включён бюджетный live-endpoint (5.3.1),
  стенд-трафик конкурирует с клиентским за реальные окна подписок. Митигируется nanoUSD-капом
  аккаунта `stage-live`, отдельным ключом (отзываемым независимо) и правилом: live-прогоны
  стенда — редкие и по расписанию, постоянная нагрузка — только на mock.

### 10.1 Решения фазы 0 (v4, утверждено владельцем 2026-08-16)

Бывшие «открытые вопросы» закрыты; формулировки ниже — обязательная часть контракта для фазы 1.

1. **Ресурсный бюджет стенда — утверждён.** MemoryMax суммарно ≤ 8 GB на все `*-stage` юниты,
   CPUQuota ≤ 200% (2 ядра), TaskMax на каждом юните; диск стенда ≤ 50 GB
   (`/opt/apitoken-staging` + `/srv/claude-api-staging` + `/var/lib/apitoken-staging`),
   билд-процессы стенда — `Nice`/`IOSchedulingClass` ниже прод-класса. Прод держит весь
   остальной запас. Бюджет подтверждён живым снятием состояния хоста (2026-08-16, SSH
   `deploy@84.32.48.2`, только чтение): RAM занято ~11 из 96 GB (available ~81 GB), диск
   326/894 GB (40%), прод-релизы занимают ~34+12+40 GB, свободной ёмкости с запасом хватает
   под бюджет стенда даже в час пик билдов.
2. **Доступ — только SSH-туннель.** Публичное DNS-имя стенду не заводится; интерфейсы стенда
   (Grafana с меткой `env=staging`, панель, API) смотрятся через `ssh -L`. UFW и Caddy-маршруты
   прода не меняются; G4 обеспечивается сетью, а не конфигурацией приложения.
3. **Песочница подписок — в фазе 7.** Набор: один минимальный Claude-тариф + один Codex +
   один Gemini на выделенных аккаунтах (НЕ из прод-флота), свой `authbot` на стенде. Если к
   фазе 7 будет включён live-endpoint (п.6) и его реализма хватает — песочницу не заводим,
   решение фиксируется отдельным коммитом в этом документе.
4. **Данные стенда — «протекающий» стенд.** Seed наполняется один раз (фаза 3), далее данные
   живут своей жизнью (история заказов/ключей/балансов накапливается, как в проде) — это
   ловит класс багов «проявляется на накопленном состоянии». Периодический reseed — по явной
   команде оператора (например, после смены формы seed или аварии стенд-БД).
5. ~~Порог «мелочи» для бай-паса стенда~~ — **закрыт отказом (v3):** байпаса нет, обход стенда
   только через `hotfix/*` с документированной причиной (разделы 6.3, 6.5).
6. **Доступ к емкости флота — фазы 1–5 только shadow-read.** Mock-апстрим стенда калибруется
   по read-only телеметрии прод-флота (окна, health, 429-профиль через Control API). Решение
   о бюджетном live-endpoint (аккаунт `stage-live` с nanoUSD-капом, 5.3.1 вариант 2)
   принимается **после фазы 5**, когда измерено, какие регрессии mock не ловит.
7. **Хотфикс-кандидаты и флот.** Кандидат-валидация хотфиксов остаётся на mock-апстриме —
   этого достаточно, т.к. хотфикс всё равно проходит полный прод-гейт. Если когда-либо
   понадобятся live-проверки хотфикса (фикс ротации под реальными 429), они идут через тот же
   бюджетный live-endpoint, что и стенд, — отдельной механики не вводится.

Портовая таблица стенда («+10000») проверена против живых слушающих портов хоста
(2026-08-16): 5434, 13000/13001, 16379/16380, 18787–18805 — все свободны; конфликтов с продом
(5433, 6379/6380, 8787–8806) нет. Точная таблица фиксируется в `docs/ops/INFRASTRUCTURE.md`
в фазе 1.

## 11. Критерии успеха (definition of done)

1. Внесённая в код деградация (латенси/ошибки/дед-подписка) ловится гейтом стенда до прода —
   подтверждено контрольной инъекцией, результат зафиксирован в аудите.
2. Нормальный деплой проходит stage→prod, хотфикс — прод с последующим схождением; оба потока
   отработаны дрилом без ручных git-операций.
3. У прод-клиентов нет ни одного сетевого пути до стенда (проверяемые UFW/Caddy-пробы
   снаружи: стенд недостижим).
4. Новая команда работает на агентском потоке так же детерминированно, как текущая:
   скрипты покрыты `.test.sh`-сьютами, документы обновлены, merge только через скрипты.
